# How multiclaude works

One bot serves several people. They reach it on Telegram and change their settings in its control panel, a Telegram Mini App. Each person has their own Claude Code session, folder, CLAUDE.md, memory and chat history. Add-ins, off until the owner turns them on, bring more ways in (Slack, Siri) and smaller features. Everything runs as one Linux user, from the repo's folder: `~/assistant` in these docs, though it can live anywhere.

![How multiclaude works: a Telegram message reaches the front desk, a Claude Code session that hosts the Telegram plugin; the router reads it there and types it into the sender's own Claude Code assistant, which replies with tg through Telegram's Bot API. The control panel and the optional Slack, Siri, locations (OwnTracks) and reminders add-ins reach the router through the relay, a Cloudflare Worker. When a browser needs the person, an assistant runs takeover, which shows them that browser live through a Cloudflare quick tunnel until they tap Done.](assets/architecture.svg)

## Core pieces

- **Front desk:** the `assistant` session, which `assistant.service` starts in tmux (`tmux -L assistant`, session `assistant`). `bin/run.sh` launches it in `~/assistant` with the Telegram plugin (`--channels`), on Haiku at low effort, with no tools, and fresh every time, with `CLAUDE_CODE_SANDBOXED=1` like the assistants, so Claude Code's "trust this folder?" dialog can't hold up the bot on a new machine before the plugin starts. It hosts the bot connection and answers nothing; `~/assistant/CLAUDE.md` tells it so. The assistants' rules are in `~/workspaces/.claude/CLAUDE.md`, outside its folder, so it never loads them. `run.sh` restarts it whenever it exits. Before each start it forgets a failed connection of the plugin in `~/.claude/mcp-needs-auth-cache.json` (Claude Code skips a server it remembers as failed, so one bad start would keep the bot offline), reapplies the plugin patch (see Questions with buttons), and runs `assistant start-users`. Only it may poll Telegram. Stock, the plugin kills whichever poller its pid file (`~/.claude/channels/telegram/bot.pid`) names as it starts, and Claude Code starts it for any session in `~/assistant`, so a `claude mcp list` run there once killed the front desk's poller and then exited, leaving the bot deaf. The patch's single poller part lets only a session started with the plugin as its channel (`--channels plugin:telegram@…`, found by walking up from the plugin's process past `bun run`) poll, take over or write the pid file; any other session gets the plugin's tools only. When the session can't be told, it polls, as stock.
- **Router:** `bin/watcher.py`, run by `assistant-watcher.service`, which gives it the same `PATH` as `bin/common.sh` gives the scripts (`~/.local/bin` and `~/.bun/bin` first), so the `claude` commands it runs can start MCP servers that need `uv`, `uvx` or `bun`; its code is the `multiclaude.router` package (see Code layout). It tails the front desk's transcript (`~/.claude/projects/<the repo's folder>/`). For each inbound message it looks up the sender's Telegram id in `users.json` and queues the message for that person's terminal. Taps in the control panel, and what add-ins' apps send, come to the router itself through the relay, never through the front desk (see Relay). It types a header line literally, then bracket-pastes the body so newlines don't submit early, then presses Enter.
  - Each session (the front desk and every person's assistant) has its own worker thread for its queue: messages, `/clear`, `/model` and `/effort` switches, `/reload-plugins` and `/mcp` commands, update restarts, and the front desk's own resets. That thread is the only thing that types into the session's terminal. The main loop only reads transcripts, routes and sends replies in the background, so one person's slow `/clear` or `/model` (half a minute) never holds up anyone else's messages.
  - It relays Claude Code's approval dialogs (`router/approvals.py`). bypassPermissions skips ordinary permission prompts, but a few built-in safety checks still stop and ask in the terminal, for example removing a workspace folder or one of its parents, and so does a tool behind an `ask` permission rule. Claude Code denies these by itself after 2 minutes. While an assistant works, its worker checks its screen every second. When such a dialog opens, the person gets the details with ✅ Approve / 🚫 Deny buttons (a question of the router's own, kind `approval`). Their tap is pressed for them: the worker moves the cursor to Yes or No, checks the screen, then presses Enter. If the dialog closes first, the question says so. An unanswered dialog that reads differently on the next check is the same one redrawn: its question is edited to the new text, with its buttons again, rather than a new one sent (a new question per redraw once sent a dozen in half a minute); only after an answer is a different dialog a new question. Nothing else is typed into a terminal while a dialog is open, since a typed digit would answer it ("1" approves at once), and a message's Enter would press Yes. The dialog's text runs from its top rule to "Do you want to proceed?", and never takes in the conversation above it, whose status dots blink: a rule followed by a borderless panel's text still counts, and without a rule the text starts after the conversation's last ●, ⎿, ✻ or ❯ line (`claude_ui.dialog_top`). The panel Claude Code can open on the right of the screen (a │ down one column, "No changes this session") is cut off first, since beside it every line ends in the panel's text (`claude_ui.without_side_panel`). A "No" interrupts the assistant's turn, as it does in Claude Code itself.
  - It saves how far it has read the front desk's transcripts in `state/router-offsets.json`, at least once a minute. After a restart (a deploy, a crash) it routes the messages that arrived meanwhile. After an outage longer than an hour it skips them rather than delivering them late. Messages already queued in memory but not yet typed are lost with a restart.
  - It handles `/clear`, `/restart`, `/stop`, `/usage`, `/model`, `/effort`, `/plugin`, `/skills`, `/mcp`, `/reload-plugins`, `/help` and `/config` per person, also when typed with a Russian or Greek keyboard layout on (`/гыфпу`, `/θσαγε` for `/usage`): `inbound.in_latin_layout` moves the letters back to their a–z keys when the command word isn't Latin and the result is one of these commands, and anything else, such as `/привет`, goes to the assistant as typed.
  - `/clear` waits until that person's assistant is idle. Meanwhile its worker posts once that it waits, with a **Cancel** button (a question of the router's own, kind `cancel-clear`, which `channels` asks and `asks.py` answers); a tap drops the `work.Clear` unless it has started, the two decided under its lock, and lets through the messages that waited behind it. Then it types `/reload-plugins --force` into the assistant, so the new conversation starts on plugins updated since the session started (forced, as `/clear` drops the prompt cache anyway; never for the front desk, whose reset leaves its Telegram plugin alone), then `/clear`, and empties that person's chat: it takes the ids to delete, posts "🧹 Context cleared" and only then deletes every message before that note from the last 48 hours (Telegram doesn't let bots delete older ones), both theirs and the bot's. The note goes first because a chat with a bot that stands empty, even for a moment, shows Telegram's big Start button, as if the person had never written to it. Bot message ids are shared by all of the bot's chats, so the ids are recorded per chat in `state/messages/<chat id>` (one `<message_id> <unix time>` line each) rather than guessed from ranges. The ids between the oldest and newest recorded ones that were never recorded are swept too, for messages the router never saw (the plugin drops contacts, polls and dice); `deleteMessages` skips the ones that belong to other chats. The router records inbound messages and its own replies, and `tg` records what it sends; `assistant notify` and jobs send through `tg`. Messages sent after a `/clear` and still waiting for delivery are kept. Add-ins with chats of their own empty them too (`after_wipe`).
  - `/model X` and `/effort X` wait until that person's assistant is idle, then type `/model` or `/effort` into its terminal, move Claude Code's picker or slider to X (checking the screen first), press `s` for this session only, and confirm the "Switch model?" cache prompt if it appears. So the shared `~/.claude/settings.json` is never written. Adding `default` (`/model opus default`) also saves X as `model` or `effortLevel` in that person's `~/workspaces/<name>/.claude/settings.json`. Claude Code lets project settings win over the shared `~/.claude/settings.json`, so their restarts and scheduled jobs start with it. A live session doesn't reload it. `max` effort can't be saved, because Claude Code ignores it in settings files.
  - `/restart` is a harder `/clear`, for a session that's stuck or should reload everything: like `/stop`, the router only sets the session's `restart_requested` (after saying it restarts, and dropping a planned pick-up), and its worker does the rest without waiting for the turn (`work.restart_fresh`). It drops a waiting `/clear` or update `Restart` from the queue, then `Session.restart_fresh` ends claude (SIGTERM, SIGKILL 10 seconds later), replaces the pane's run loop with `bin/run-user.sh <name> fresh` (`tmux respawn-pane -k`), which starts claude without `--continue` the first time, and waits up to a minute for it. A new run loop, rather than a flag for the old one, because a running bash loop never rereads its script. Then the session-only switches are typed in again, and the chats are emptied as after `/clear`, the note saying it restarted. Messages sent meanwhile wait for the new claude.
  - `/stop` is the Escape key, which Claude Code has no command for: the router cancels a planned pick-up (below) and sets the session's `stop_requested`, and its worker, the only thread typing into that terminal, presses Escape (`Session.stop`). That's confirmed by the note Claude Code writes, "[Request interrupted by user]" (or "… for tool use]"), which also ends the turn in `turn.Turn`, since an interrupted turn writes no `turn_duration`. Messages typed into the turn still come next, as after Escape at the terminal. With no turn running there's nothing to stop, so nothing is pressed.
  - `/help` (`router/about.py`) sends, at once, what that app takes (Telegram: text, photos, files, audio, video and replies, plus what the add-ins that are on add), the other ways in the person has, and the command menu's entries. Stock, the Telegram plugin answers `/help` itself with its pairing help, so `bin/patch-telegram-plugin` passes a paired sender's `/help` on like any message. What their assistant can do with their MCP servers is theirs and changes, so the router then types a `[Router · …]` note into their assistant (`about.mcp_note`), which answers with one line per server it has. The same module holds the command menu (`about.COMMANDS`, set per chat with `setMyCommands`) and the bot's description, the "What can this bot do?" box of an empty chat, and its short description on the bot's profile, both naming the owner from users.json; the router sets them with `setMyDescription` and `setMyShortDescription` when it starts.
  - It handles `/plugin` (and Claude Code's alias `/plugins`) and `/skills`, named and used as in Claude Code: `/plugin install <plugin>@<marketplace>`, `/plugin install <marketplace>` to browse, `/plugin directory [word]`, `/plugin enable|disable|uninstall`, `/plugin marketplace add|remove|update|list`, and `/skills off|on <name>` (Claude Code has no `/marketplace` command, so neither does the bot). In a background thread it runs `bin/shared.py command <name> <text>`, which makes the change with `claude plugin … --scope project` (or `skillOverrides`) in that person's workspace only, runs the shared sync (see Shared bits), and returns the reply. After a change it queues `/reload-plugins`: once the assistant is idle the router types it in and sends back Claude Code's "Reloaded: …" line, read from the transcript, where it's a system entry. Uninstalling or disabling a shared plugin turns it off for that person, which sends it back to the others' folders. `/skills on` for a skill that went back that way copies it from someone who has it. Shared marketplaces can't be removed, and the Telegram plugin can't be installed (a second copy would take over the bot). Claude Code's subcommands don't apply the `env` of the folder's settings the way its sessions do, so every `claude` command the bot runs in a folder (`claude_cli.env_for`, `/mcp login` included) gets the `env` from that folder's `.claude/settings.json` and `settings.local.json`: a person's own GitHub login there (`GH_CONFIG_DIR`, `GIT_CONFIG_GLOBAL`) also clones their private marketplaces.
  - It handles `/mcp` as in Claude Code: `/mcp` lists the person's servers with their health (`claude mcp list` in their workspace), `/mcp get|add|add-json|remove|logout <name>` run `claude mcp …` there, and `/mcp enable|disable|reconnect <name>` are typed into their assistant once it's idle, like `/reload-plugins`, with Claude Code's answer sent back. MCP servers are never shared: a server often carries a login, so each person keeps their own at Claude Code's local scope (`~/.claude.json`, under their workspace), which only their assistant loads. Because every session runs as the same Linux user, Claude Code's stored MCP OAuth tokens would be shared between two people with the same server name and URL (it keys them by name, type, URL and headers), so `bin/shared.py` adds an `X-Assistant-User: <name>` header to every URL server it adds. A running session doesn't see a server added on the command line until `/reload-plugins`, so after `/mcp add` the router types `/reload-plugins` and `/mcp reconnect <name>`; after `/mcp remove` it types `/mcp disable <name>` (a removed server stays connected otherwise), and a later `/mcp add` of that name types `/mcp enable` first. `/mcp login <name>` runs `claude mcp login <name> --no-browser` on a pseudo-terminal (it refuses to read the redirect URL from anything else), sends the sign-in link, and passes on the `http://localhost…?code=…` address the person pastes back within 10 minutes (`/mcp login cancel` stops it); on success the assistant reconnects the server. Phone keyboards' smart quotes and `--`-turned-dash are undone first.
  - It reloads an assistant that asks for it. An assistant can't type a slash command into its own terminal, so after it installs or updates a plugin or skill itself it runs `assistant reload-plugins --user <name>`, which leaves an empty file `state/reload-requests/<name>`. Every poll the router takes those files (`plugins.take_reload_requests`) and queues one `work.Reload` for that person, the same one a `/plugin` command queues: it types `/reload-plugins` once the assistant is idle and sends the person Claude Code's answer. A person can send `/reload-plugins` too, or `/reload-plugins --force`, which a waiting reload takes on. Claude Code holds back a reload that changes MCP tools, since that costs the prompt cache, and answers that it needs `--force`; the router passes that answer on with a 📋 button for `/reload-plugins --force`.
  - It keeps "typing…" on while a person's assistant works, by tailing that person's transcripts (`turn.Turn`): from a queued message until the turn that handles it ends. A queued item Claude Code only writes down, starting no turn (`queueTranscriptOnly`, such as its report after a restart on a background task the old process left running), leaves an idle assistant idle, so it isn't judged stuck 15 minutes later. Those calls run in the background, so a slow Bot API call never holds up routing.
  - It keeps its Bot API connections open between calls and opens new ones over IPv4 first, with IPv6 tried shortly after: on some networks new IPv6 connections to Telegram hang for seconds while IPv4 connects at once. `tg` uses the same client.
  - It tells a person when their assistant fails mid-request: the turn ends on an API error (502, auth, rate limit…), the session's claude process restarts mid-turn, or 15 minutes pass with no transcript activity (subagent transcripts count; that clock stops while the machine is offline).
  - It has an assistant pick up a request by itself when its turn ended on an API error that may pass: no answer from the API at all, or a failure on the API's side (5xx, overloaded), but not a login, billing or plan limit problem or a refused request (`router/recovery.py`). The person is told it will carry on. Once a wait is over (a minute, then 5 minutes for a second one), the network is up and the assistant is idle, the router types a one-line `[Router · …]` note asking it to pick up where it left off, naming the outage if there was one. That happens at most twice an hour per assistant; after that, and for other errors, the person is asked to send their message again. A new message from them replaces a pick-up that's still waiting, since the assistant carries on anyway. A pick-up still waiting is lost if the router restarts.
  - It gets going again after the machine loses its network. In an outage, connections already open can keep working while no new one gets out, so assistants can think but not reply. A background thread (`recovery.Network`) opens a new TCP connection to the Bot API and to the Claude API the sessions use (`ANTHROPIC_BASE_URL` from `~/assistant/.env`, else Anthropic's) every 15 seconds, every 5 while offline; two failures in a row mean the machine is offline. While it is, the router shows no "typing…" and judges no turn stuck. Messages that can't reach Telegram are held (see Replies). Once the network is back it sends what was held, and after an outage of 3 minutes or more it tells the owner, silently.
  - It keeps the bot listening (`router/poller.py`). Claude Code never starts a plugin's server again once it has exited, so if the poller goes while the front desk's claude stays up, nothing reaches the bot and nothing says so. Every 15 seconds the router checks that the plugin's pid file names a `server.ts` under the front desk's claude. After 90 seconds without one it ends that claude (`run.sh` starts it again, with a new poller), at most once every 5 minutes, and tells the owner, silently. Telegram keeps what was sent meanwhile, so it arrives then.
  - Every 40 routed messages it sends the front desk a `/clear`, to keep that session's context small.
  - It keeps Claude Code current. Every 30 minutes it runs `~/.local/bin/claude update` in the background (the native installer puts each version in `~/.local/share/claude/versions/` and repoints that link). Every minute it compares the version each session's claude process runs (from `/proc/<pid>/exe`) with the link's target. A session that is behind, the front desk included, gets `/exit` typed into it (SIGTERM after 20 seconds) once it is idle: no turn running or queued, no Bash tool command still running under it (background tasks and monitors count; they're recognised by `.claude/shell-snapshots/` in their command line), and no transcript write, subagents included, for 5 minutes. Its run loop starts it again on the new version, and a person's assistant resumes with `--continue`, which appends to the same transcript. Messages that arrive meanwhile wait until it's up. Session-only `/model` and `/effort` switches are typed in again afterwards, since a restart drops them. Once every session has moved, or after 6 hours if one is still too busy (named in the message), the owner gets one Telegram message listing who was restarted and anyone still on the old version after its restart. Each session is restarted at most once per version. Session-only scheduled tasks inside Claude Code (CronCreate, /loop) don't survive a restart; the crontab does.
- **Per-person assistants:** tmux sessions `u-<name>`, each running `bin/run-user.sh <name>` in `~/workspaces/<name>`. Every one is full admin (`--permission-mode bypassPermissions`), resumes its last conversation after a restart (`--continue`), and is started by `assistant start-users`. `run.sh` calls that before every front desk start, and the router calls it when a session is missing. A session that exits within 30 seconds of starting is started fresh the next time rather than resumed, in case its conversation is what breaks it. `run-user.sh` sets `TG_CHAT_ID` and `ASSISTANT_USER` for `tg` (and the add-ins' commands), turns the Telegram plugin off (a second copy would take over the bot), and sets `CLAUDE_CODE_SANDBOXED=1`, which makes Claude Code trust the workspace, so its "trust this folder?" dialog never holds up a session nobody watches. Their memory lives in `~/.claude/projects/<their folder>/memory/`.
- **Replies:** `bin/tg` (also linked as `~/.local/bin/tg`), a Python program on the same Telegram client as the router (`multiclaude.telegram`), calls the Bot API directly: send (with files), ask, edit, react, typing and download, plus the commands add-ins add (`tg_commands`). It records each message it sends in `state/messages/` for `/clear`. tg and the router lock a chat's record file (`<chat id>.lock`) while they write or wipe it. It sends to `$TG_CHAT_ID`, which `run-user.sh` and `assistant job --user` set to that person's chat, or to `--chat ID`.
  - Held messages: when Telegram can't be reached (`telegram.Unreachable`: the connection failed, so nothing was sent), `tg send` holds the message in `state/outbox/<chat id>/`, with copies of its files, and exits with 75. `assistant notify` and jobs count that as sent. The router's own messages (`telegram.send`) are held the same way. A chat's held messages go out in order before anything new to that chat: with the next `tg` or router message to it, or from the router once its network check sees the network back (and every 30 seconds while any are left). One that goes out more than 2 minutes late ends with "⏳ Written at 09:18 and held until now…", in the person's timezone. A held message Telegram refuses, or one held for over 24 hours, is dropped. `tg ask`, `edit` and `react` are never held; they fail as before. Neither is a call that reached Telegram but got no answer, since it may have arrived. New connections give up after 10 seconds (`CONNECT_WITHIN`), so `tg` holds a message well within the Bash tool's 2-minute timeout.
- **Name:** the bot's name is `name` in `config.json`, which `assistant setup` fills in from Telegram's `getMe` and the owner may change; `aka` adds a second name, shown next to it in the bot's description (`bot.full_name`). Without one it is "Claude". Everything the bot says to people calls itself "I" or by that name, never "your assistant": the assistants' rules get it as `{{BOT_NAME}}`, the router's notices use `bot.name()`, and the control panel's snapshot carries it (the page says "the bot" until one comes). `assistant` stays the name of the command.
- **Formatting:** every message is a Telegram rich message (`sendRichMessage`), which shows real headings, lists, tables, quotes, code blocks and collapsible sections. `tg send`, `tg ask` and `tg edit` take GitHub-flavored Markdown written by the assistant, following "Formatting" in `system/workspaces-CLAUDE.md`. `tg send --file` uploads the files as media blocks below the text, in the same message. With `--separate` it sends the text alone and then each file as a plain `sendPhoto` or `sendDocument` message, since a file inside a rich message doesn't forward well: for files that are alternatives to one another, so one can be forwarded alone. A held file sent this way gets no late note; the text before it has one. A rich message holds 32,768 characters, so `tg` cuts longer text at line breaks. The router builds its own messages as explicit blocks instead of Markdown, so Claude Code's output and other text in them is never misread as formatting. Its texts are plain text with commands, paths and names in backticks (`` `/mcp login x` ``, `` `assistant status` ``), as are the `/plugin`, `/skills` and `/mcp` replies. `telegram.rich_blocks` makes each part between blank lines a paragraph and each backticked span inline code; outside code, Telegram would make a bare `/command` a link that sends it. Telegram doesn't copy anything in a rich message on tap, code blocks included, so a 📋 `copy_text` button under the message copies what the person should paste somewhere (`telegram.copy_buttons`, up to 8 of at most 256 characters). Buttons are only ever named explicitly, never derived from code formatting, since a button on every path and name would bury the few that matter: `tg send --copy TEXT` and `tg edit … --copy TEXT` (refused when a button can't hold TEXT), `telegram.send(…, copy=[…])` in the router, and a `/plugin` or `/mcp` reply's `copy` list. The router adds them only for a command the person may send next, such as `/mcp login x` after a server says it needs a sign-in. Approval questions show the dialog as a preformatted block. Telegram renders a highlight unreadably in its dark theme, so `tg` sends any outside code as bold (`telegram.without_highlights`).
- **Questions with buttons (`tg ask`):** `tg ask "Question?" "A" "B"` sends the question with one inline button per option (callback data `ask:<n>`) and saves the question and options in `state/asks/<chat id>/<message id>.json` (deleted after 30 days). Only the plugin may poll Telegram, and stock it drops taps on buttons it didn't make, so `bin/patch-telegram-plugin` adds a branch to its callback handler in the plugin cache (`~/.claude/plugins/cache/claude-plugins-official/telegram/<version>/server.ts`). Each version's original is kept as `state/telegram-plugin/<version>-server.ts`, and every run rebuilds `server.ts` from it with the core's patches and those of the add-ins that are on, so turning an add-in off takes its patch out. A tap on an `ask:` button from an allowed sender in a private chat reaches the front desk like an inbound message, with the button label as text and `callback_id` and `callback_data` in its meta (`message_id` is the question's). `run.sh` runs the patch before every front desk start, since a plugin update brings a fresh copy; if a new version's code no longer matches a patch, it leaves that patch out and tells the owner once. The router dedupes taps by `callback_id`, takes the full label from the saved options, and right away replaces the buttons with the question plus "👉 <choice>" (so a second tap can't happen, and one that races in is ignored), records the answer, then types the choice into that person's assistant. The assistant then edits the question to say what it will do. A typed answer works too; the assistant removes the buttons by editing the question. The router's own questions (approvals, a waiting `/clear`) are kept the same way with a `kind` (`multiclaude.questions`) and answered by `router/asks.py`.
- **Reply context:** `bin/patch-telegram-plugin` also patches the plugin's inbound handler so that a message replying to another one carries `reply_to_message_id`, the replied-to text as `reply_to_text` (a rich message flattened to plain text, cut at 3000 characters) and the part the person quoted as `reply_quote`. The router adds "Replying to msg N:" and that text, quoted, after the message text it delivers.
- **Reactions:** Telegram sends a bot reactions only when its poller asks for them, and stock the plugin doesn't. `bin/patch-telegram-plugin` adds `message_reaction` to the update types it polls for (grammY's defaults plus it) and a handler: an emoji a paired sender adds to a message in their private chat reaches the front desk like an inbound message, with the emoji as its text and as `reaction` in its meta (a Premium custom emoji as the emoji it stands for), and `message_id` the message reacted to. Taking a reaction off sends nothing. The router keys a reaction by that message, the emoji and the time, so it isn't taken for the message itself, doesn't record the message id again, and types it into the person's assistant as one line with nothing pasted: `[Telegram from <Name> · reaction on msg N · …] I reacted with 👍.` Each reaction is a turn of the assistant's; it replies only when the reaction asks for something.
- **Formatted messages:** a message a person formats in Telegram (headings, lists, code, tables) arrives as `rich_message` with no `text`, and stock the plugin drops it without a word. `bin/patch-telegram-plugin` adds a handler after the plugin's text handler that passes it on as GitHub-flavored Markdown (`multiclaudeRichMarkdown`): headings, lists with their numbers and checkboxes, bold, italic, strikethrough, spoilers, code, links, code blocks, quotes, tables and collapsible sections. Photos, files and other media inside it become a note in the text, `(photo · file_id: …)` or `(document: name · file_id: …)`, with their caption, and the assistant fetches them with `tg download` like any attachment (the largest size of a photo). Maps become their coordinates and buttons their labels.
- **Registry:** `users.json`, keyed by name: `{"ada": {"telegram_id": "…", "display": "Ada", "role": "owner"}}`. `role` is `owner` or `member`; the owner is the default target for `assistant notify` and `assistant job`, hears about updates, outages and the machine's health, and sees the machine in the control panel. `timezone` (an IANA name, UTC when missing) sets the times the router shows that person, in held-message and outage notes. Add-ins keep their own fields there too (`slack_id`, `quiet_hours`, `restore_model`), read from the entry as it is (`User.get`, `Session.entry`); fields nothing knows are ignored.
- **Assistant rules and personal CLAUDE.md:** how every assistant works (Telegram and `tg`, the shared machine, what the router handles, plugins, skills, MCP servers, jobs) is in `~/workspaces/.claude/CLAUDE.md`. `assistant install` (and `setup`, and `addon enable|disable`) renders it from `system/workspaces-CLAUDE.md`, filling in `{{ROOT}}` (the repo's folder, since cron lines need absolute paths), `{{USER}}`, `{{BOT_NAME}}` and `{{BOT_USERNAME}}`, and appends the `addons/<name>/rules.md` of each add-in that is on, filled in the same way. Claude Code loads a parent folder's `.claude/CLAUDE.md`, so every session under `~/workspaces/` reads it, jobs included, and nothing else does: not the front desk, not other Claude sessions on the machine. It is written for any person ("your person", `<name>` = the folder name). Each person's `~/workspaces/<name>/CLAUDE.md` is short and personal: who they are, their short name and folder, and what every session must know about them. It is rendered once from `templates/CLAUDE.md.tmpl` when the person is added; after that it belongs to them and can be edited freely.
- **Relay:** a Cloudflare Worker in `relay/` (free plan), the way in from the internet for the control panel and for the apps add-ins bring. Nothing reaches the machine directly: the router connects out, so nothing on it is published (only a browser take-over's page is, through a tunnel that also connects out and lasts as long as the take-over), and what comes while the machine is offline waits at the relay. The Worker keeps each envelope (`{envelope_id, type, payload}`, Slack's Socket Mode shape) in its one Durable Object (SQLite) until the machine acknowledges it, dropping what nobody collected in a day. `router/relay_entrance.py` holds a WebSocket to the relay's `/queue` (`lib/multiclaude/websocket.py`, a small standard-library client, since the bot's Python has no dependencies) with `Authorization: Bearer <relay_token>`. On connecting it gets "hello" and everything still kept, then each new envelope as it arrives; it acknowledges each and queues it for the loop, so a tap made while the machine was offline is carried out once it's back. A connection quiet for 2 seconds is pinged and one silent for 6 is dropped and opened again at once. The router takes `panel` envelopes itself and hands other types to the add-in that takes them (`relay_envelopes`); a type nothing that's on takes is logged and dropped. What goes back to the relay (a panel snapshot, an add-in's answer) is a PUT with the relay token. A request that needs the machine's answer, such as Siri's, OwnTracks' or a Reminders shortcut's, is held by the Durable Object until the router puts one or a time limit passes (`vm.js`, `askVm`). `assistant relay deploy` deploys the Worker `assistant-relay` with `wrangler` (version pinned in `bin/assistant`) and the token in `state/cloudflare.json` (`api_token`, `account_id`; readable only by the owner's user), making the account's workers.dev subdomain if it has none. It sets the secrets `RELAY_TOKEN` and `TELEGRAM_WEBAPP_KEY` (below), passes the add-ins that are on as the variable `ADDONS`, runs each one's `addons/<name>/relay-deploy`, saves `relay_url` and `relay_token` in `state/relay.json`, and restarts the router, which reads it as it starts.
- **Control panel:** `/config` (Claude Code's name for its settings panel) answers with a button that opens a Telegram Mini App, and so does the **Panel** button by every private chat's message box, in place of ☰ Menu (the commands still show when you type /), which the router sets with `setChatMenuButton` when it starts (`panel.set_menu_button`). Without a relay, `/config` says so. The Mini App is a page served by the relay from `relay/public/app/`. It loads Telegram's Mini App script from its own copy (`telegram-web-app.js`, telegram.org's version 64; download it again to update), since some Telegram clients can't load it from telegram.org, and without it the page can't tell who opened it. It shows the person their model and effort, context and plan limits, their scheduled jobs with the next run of each, what those jobs did (Activity), their MCP servers with their health, their plugins and skills, and their name and timezone, plus the settings of the add-ins that are on (`panel_fields`), and the owner (by `role` in users.json) also the machine's health (see Machine health), and changes them with a tap: the model and effort through the router's own `/model X` and `/effort X`, with `default` added while the page's **Keep after restarts** switch is on (kept per device in localStorage; max effort is never kept), an MCP server through `/mcp reconnect|enable|disable|login <name>` (answers come in the chat as usual), a plugin or skill through `/plugin enable|disable <plugin>@<marketplace>` or `/skills on|off <name>`, run as the bot runs them when they're sent (`plugins.run`: the reply in the chat, then a reload) and followed at once by a new snapshot with the result, a setting in their own `users.json` entry (`users.update`), a job paused or resumed in the crontab (`cronjobs.py`: its lines commented out behind `#⏸ `, and back exactly), or deleted by their assistant, which gets a `[Control panel from <Name> · …]` request and also updates jobs.md. The page shows what the router last put on the relay, so it opens at once even while the machine is offline. Telegram signs who opened it (the init data, HMAC-SHA256 with a key derived from the bot token); opened without that (a plain link, or a client that passes none), the page says so and shows the platform and Mini Apps version Telegram reported and whether the address carried sign-in data, so a screenshot tells which client failed. The relay checks the signature with `TELEGRAM_WEBAPP_KEY`, the derived key, which checks signatures but can't drive the bot (`relay/src/panel.js`), before it answers `/app/state` or queues a tap from `/app/action` as a `panel` envelope; the router checks it again with the bot token (`router/panel.py`, `signed_sender`) before it changes anything, trusting a signature for a day. The router puts each person's snapshot at `PUT /panel/<telegram id>`, but only when it changed: every 30 seconds it builds it and compares its fingerprint with the one it last put (kept with the snapshot in `state/panel/<name>.json`, so a restart doesn't put it again). Usage counts as changed in steps of 5% (context, plan limits) and $1, and reset times to the minute, so a working session doesn't put one every turn. An answered tap always changes it. Opening the panel is one read of `/app/state`; after a tap the page reads with `{after: version}`, and the Durable Object holds that read until a newer snapshot arrives (at most 25 seconds), so a tap costs about two requests instead of a poll every second. Plugins and skills are a section of their own, Plugins and Skills on two tabs, one line each with tags for what a plugin brings (tools: an MCP server, skills, code: a language server) and a switch, opened with a tap for its description and where it comes from. `sharing/inventory.py` reads them for each snapshot from files only: the person's settings (`enabledPlugins`, `skillOverrides`), each plugin's folder (in its marketplace when it's there, which is how a directory marketplace is read in place, else where `installed_plugins.json` says Claude Code put it) with its `.mcp.json`, `.lsp.json`, `skills/` and `plugin.json`, its marketplace entry, and each skill's SKILL.md (its description up to "Use when…"); a marketplace catalog is parsed once per version. It lists the plugins the person has on or turned off (never the front desk's Telegram plugin), and their own skills, the shared ones and any other they turned off; a plugin's skills come and go with it. The page shows a switch as asked for until a snapshot has it (at most two minutes). When the last MCP check is over 10 minutes old, opening the panel also asks for one (`claude mcp list` in their folder, about 5 seconds, with the plan's limits fetched again), and a second snapshot follows with the result. The Activity lists their latest 50 job runs from their record (`jobruns.py`, see `assistant job` under Shared bits), newest first: when each started, in their timezone, how it went, what it cost, and the start of its answer as plain text, cut to two lines until it's opened. A run shows under its job's name when one of that job's crontab lines gives `assistant job` the same instructions (`cronjobs.Job.prompts` reads them from the line as the shell would, near enough, and `jobruns.title` titles them as the job does); a run of anything else keeps its own title. Above them are the runs, failures and cost of today, in their timezone, and of the last 7 days, counted over every run kept. How the page words times, money, sizes and runs is in `relay/public/app/format.js`, apart from the page, so the relay's tests check it. The owner's snapshot alone has `machine` (`panel.machine_part`): the latest sample kept by `assistant health sample` with the alerts standing then, the day up to it in 96 quarter hours, each the highest sampled (`history.last_day`), for a sparkline each of CPU, RAM and the fullest disk, and where each counts as high, which the page draws as a dashed line. The day is anchored on the sample's time, not the clock, so the owner's snapshot changes, and is put again, only with a new sample, every 5 minutes. The page draws the bars and the SVG sparklines itself (`sparkline.js`, also tested on its own); a finger on a sparkline reads the share at that time, and a sample over 15 minutes old says so, since the router puts nothing new while it, or the machine, is down. Snapshots are kept in the Durable Object, one per person.
- **Machine health:** `assistant health sample` (`bin/health.py`; code in `lib/multiclaude/health/`), which cron runs every 5 minutes (a line `assistant install` adds), reads the machine: how busy the CPU was since the sample before (from `/proc/stat`'s counters, kept with each sample), the load averages and the cores, RAM used (what `MemAvailable` doesn't count as available) and swap, each file system holding `/`, the repo or the workspaces (used as `df` counts it, without root's reserve), the uptime, the 5 programs using the most memory, the apps hosted in Podman, whether systemd has the router active, and whether claude runs in each person's tmux session (the session's shell has a claude child; people without a folder are left out, as `assistant start-users` leaves them). A hosted app is a pod of the user's rootless Podman, or a container outside any pod, read from `podman ps --all --pod` (with `XDG_RUNTIME_DIR` filled in, which cron leaves out): how many of its containers run (a pod's infra container, which runs nothing, isn't counted) and the memory of each running container's process and everything it started. Without Podman there are none, and the panel shows no Hosted section. A program's memory is the sum of its processes' proportional set sizes (`Pss` in `/proc/<pid>/smaps_rollup`, which splits shared pages among the processes sharing them; root's processes, which it can't read, count their resident size): a browser's dozens of processes share most of what they hold, and their resident sizes added up came to twice the machine's whole used RAM. Programs are named so the owner knows whose they are: Chrome for all of a browser's processes, `claude (ada)` by the working folder (`claude job (ada)` for a `claude -p`, `claude (front desk)`), an interpreter by its script or module (the router by its role), and a name the kernel cut at 15 characters as the command line has it.
  - It keeps the sample in `state/health/latest.json` (with the counters and the alerts standing) and its shares in `history.jsonl`, a week of them, then checks the rules (`alerts.py`), each standing fine, high or, for a disk, critical (`alerts.json`). A share goes up after N samples in a row at or over its line and down at once, but only under a lower line, so a value at a line doesn't flap: CPU 90% for 3 samples, clear under 70%; RAM used 90% for 3, under 80%; swap 50% for 3, under 40%; each disk 85% at once, under 80%, and critical at 95%, easing back under 90%. The router is high as soon as it isn't active, a person's assistant once it has been missing for 2 samples. A sample that doesn't know a share (the CPU, at the first sample or after a reboot) leaves its rule as it was. The owner's `config.json` can change any of these numbers (`"health": {"ram": {"at": 95}}`).
  - The owner gets a message when a rule goes up a level or back to fine, never while it stays put: what, the numbers now, and for CPU, RAM and swap the top memory users. It goes out with `assistant notify`, through the Bot API itself, never through the router, so a router that's down is reported like anything else, and it's held while Telegram can't be reached. A rule whose message couldn't be sent keeps its standing from before, so the next sample tells it. A sample still running makes the next one skip (`sample.lock`). The machine can't report its own end: then the samples stop, and the control panel shows how old the last one is.
  - `assistant health` (or `health status`) prints the machine now, with the CPU watched for a second, the hosted apps, and the alerts and the day's highs from the samples kept.
- **Browser take-overs:** `bin/takeover` (linked into `~/.local/bin` like `tg`; code in `lib/multiclaude/takeover/`) hands an assistant's browser to its person when it hits something only they can do: a CAPTCHA, a press-and-hold check, a 3-D Secure confirmation, a consent screen. The assistants browse with `agent-browser`, and each of its sessions runs a WebSocket stream server on 127.0.0.1 that sends a JPEG frame of the page whenever it changes and takes mouse and keyboard events (`agent-browser --json stream status` names its port; `stream enable` turns it back on). `takeover --session NAME` checks `session list` first, since any other agent-browser command for a session that isn't running starts one. It connects to the stream (a thread keeps only the latest frame), serves the page from a threaded `http.server` on 127.0.0.1, and opens a Cloudflare quick tunnel to it (`cloudflared tunnel --url`): a random `https://….trycloudflare.com` address, read from cloudflared's log once its connection is registered, with no account, DNS or open port. A new address can take some seconds to resolve, so the link waits until the page's server answers there (its 404 for a request without the token), up to 30 seconds. The link, that address and a random 32-byte token, goes to the person's Telegram chat as a Mini App (`web_app`) button, so Telegram fetches no preview of it, with what they should do (`--for`). Opened that way, the page tells Telegram to expand its sheet, ignore vertical swipes (in Telegram's iOS app a downward drag, which is how the person scrolls the browser, would otherwise pull the sheet away) and ask before closing; in Safari or a desktop browser there's no Telegram to tell. It isn't held when Telegram can't be reached, since it would be dead by the time it went out.
  - The page (`takeover/page.html`, with its script and styles inline, for Telegram's in-app browsers) is the browser, full screen, under a slim bar: the task on one line, **?**, **I can't do it** and **Done**. A tap on the task or the **?** opens a panel over the browser, so it keeps its size, with the task in full, how the link is doing and how the page works; the connection's state shows over the browser only while it isn't live. Nothing on the page can be selected or long-pressed into a callout. It draws each frame on a canvas and asks for the next one at once (`frame?after=N`, which the server holds until a newer frame comes, up to 20 seconds).
  - The browser is fitted to the screen (`takeover/viewport.py`). As the page opens, and once its room has stayed put for 300 ms after a change (a window resized, a phone turned), it reports the CSS pixels it has for the browser (`screen`), and the server sets the session's viewport to that, within 320–2560 by 320–1600 (`agent-browser set viewport W H SCALE`), so each frame shows 1:1 on a phone and a laptop alike. The scale stays the page's own: the stream's frames are CSS pixels at any scale, so a sharper one wouldn't reach the screen. Before the first change the server reads the viewport as the page sees it (`eval` of `innerWidth`, `innerHeight` and `devicePixelRatio`), and it puts that back when the take-over ends, unless the browser has closed, since any agent-browser command for a session starts it again. A fit or a restore agent-browser fails is logged on stderr, and the page then shows the frames scaled. While a phone's keyboard is up the page reports nothing, so the browser keeps its size (below).
  - With a mouse (the browser reports a fine pointer, or a mouse moves over the page) the person works in the browser itself: a click with any button, a double or triple click, hovering and dragging, and the wheel or trackpad scrolling where the pointer is. A click puts the focus on a hidden textarea at that point (where an input method shows its candidates), as does a key pressed while nothing on the page has the focus (a physical keyboard). Keys that type nothing (Enter, Tab, Escape, Delete, the arrows, Home, End, Page Up and Down) and Control or ⌘ with A, C, X, Y or Z go as keys, with ⌘ and ⌥ sent as Control, which does their work on the browser's Linux. Every other key types into the textarea, as on a phone (below).
  - With a finger, what it does is known once it moves, lifts or stays put. A quick tap clicks where it went down, with no move between the press and the release, so it selects nothing; two taps close together double-click. A drag scrolls the box under where it started, by wheel turns as far as the finger went, and a finger lifted while still going flings the page on, slowing down as a phone's does. A finger held still for 450 ms presses there (a ring shows it) and drags with the button down until it lifts: a slider, a "press and hold" check. Two fingers zoom the page (`touch-action: pinch-zoom`), and a second finger cancels whatever the first was doing.
  - A phone brings its keyboard up only for a focus made while a touch ends, too soon to ask the browser what the tap focused. So the page keeps a map of the text fields in view (`GET fields`, `takeover/fields.py`): one `eval` finds the inputs, textareas and editable elements on top where they are, and their labels, in open shadow roots and same-site frames, as fractions of the viewport, with the keyboard each brings up on a phone (its `inputmode` or its type's, a numeric one for a code; capitals and corrections as the field asks or as phones do for its type). The page looks again whenever a new frame came, at most every 500 ms, and once the browser has closed `fields` answers 410 without asking. A tap on a field focuses a hidden textarea over it with that keyboard as the touch ends, and a tap anywhere else, or beside the frame, puts the keyboard away. Once the tap's release is through the page looks again: if a field it didn't know of took the focus (a click-to-edit widget), the floating ⌨ button stands out, since only a tap brings the keyboard up now; if nothing to type into has it, the keyboard goes down; a focus inside a frame from another site can't be looked into, so it changes nothing. ⌨ also brings the keyboard up by hand, and ⌫, ↵ and ⇥ buttons show while it's up.
  - Typing goes as it happens. The textarea keeps what the keyboard typed since the caret last moved some other way, and each change goes as the difference: the caret moved by arrow keys to the end of what was taken away, a Backspace for each character of it (as a person counts them, `Intl.Segmenter`), and the new text. So autocorrect, predictive text, input methods (Android's keyboard composes every word), dictation, pastes and any alphabet type into the browser what they would in a field of its own. Enter, Tab, the arrows and the shortcuts go as keys and start the textarea afresh, and so does Backspace with nothing typed before the caret, which deletes what the field had.
  - With a phone's keyboard up the browser keeps its size. The page follows `visualViewport` to take only the part of the screen above the keyboard, and scrolls the frame so the tapped field stays in sight with some room below it; the meta viewport's `interactive-widget=resizes-visual` makes Chrome on Android shrink only the visual viewport, as iOS does. A keyboard that goes down while the textarea keeps the focus (Android's back button) ends the typing, so the next tap on a field brings it up again.
  - The page's actions go back one at a time, in order, so a press always arrives before its release; moves, wheel turns, typed text and presses of the same key waiting in a row go as one (a key action's `times`). The server turns their points and wheel turns, fractions of the frame, into the page's CSS pixels: by the width's scale on both axes, since until the viewport is fitted the frame shows the window's viewport, which can be shorter than the `deviceHeight` the stream reports. It sends the stream's events with every field filled in, because the stream server drops an event missing one (a Backspace without `text` never arrives). A connection the page drops mid-answer (cloudflared hangs up the ones it holds as the tunnel closes) is no error.
  - It ends with **Done** or **I can't do it** on the page, the time limit (`--minutes`, 15 by default), the browser closing, or a stop signal (a stopped background task gets SIGTERM). The tunnel, the server and the stream close, the viewport is put back, the Telegram message is edited to say how it ended, and the command prints one line and exits 0 for Done, 3 for I can't do it, 4 when the time ran out and 1 otherwise. The assistant runs it as a background command, so it hears the moment it ends.
  - The frames show whatever the browser shows, payment pages included. So every path is under the token, compared in constant time, and anything else gets 404, as does plain HTTP through the tunnel; nothing is logged, since request lines carry the token, and cloudflared logs only its connections; responses are never cached and send no referrer; the tunnel lasts only as long as the take-over; and only one take-over of a browser runs at a time (a lock per stream port in `state/takeovers/`). `--home` asks agent-browser under another HOME, for a session a plugin runs under its own (its sockets are in that HOME's `.agent-browser/`). `--print-link` prints the link instead of sending it, to try a take-over on the machine.

## Add-ins

An add-in is a feature that is in the repo but on only while the owner lists it in `config.json` (`{"addons": ["voice-notes", "quiet-hours"]}`); the core works fully with all of them off. `assistant addon list|enable|disable <name>` manages the list. Enabling runs the add-in's `setup`, if it has one, and leaves it off if that fails; disabling runs its `teardown`, if it has one, and leaves it on if that fails. Either way the assistants' rules are rendered again, this install's router is restarted (it reads some of an add-in's part only as it starts), and the add-in's `next-steps` are printed.

- **The list:** `multiclaude.addons.ALL` names every add-in; `addons.names()` gives those `config.json` turns on, reading the file again only when it changes, since it's asked on every message sent and every transcript entry. The bash scripts ask `addon_on` in `common.sh`, and the plugin patcher reads `config.json` itself.
- **Code:** an add-in's code is a module or package in `lib/multiclaude/addons/` named after it (`voice_notes.py`, `slack/`); an add-in may have none. The core never imports an add-in. It calls hooks (`addons.call`, or `addons.through` for a value each add-in may change), each run for every add-in that is on and defines it, in `ALL`'s order. A hook that fails is logged and skipped, so an add-in never breaks the core. The hooks, documented in `lib/multiclaude/addons/__init__.py`:
  - `on_transcript_entry`: each new entry of a person's transcript, before the turn sees it (not the entries replayed at startup).
  - `before_telegram_send`: every message any sender posts (`telegram.BotApi.call`).
  - `on_message`: a message for an assistant, which an add-in may queue its own way.
  - `attachment_lines`: lines for a message's Attachments.
  - `help_info`: what `/help` and the bot's description say a person can send in an app, and the other ways in.
  - `panel_fields`: `users.json` fields the control panel shows and sets, with their checks; the snapshot lists the add-ins that are on, so the page shows only their settings.
  - `relay_envelopes`: the relay envelope types the add-in takes.
  - `after_wipe`: `/clear` or `/restart` emptied the person's Telegram chat; empty the add-in's own chats too.
  - `tg_commands`: commands the add-in adds to `tg`.
  Add-ins may offer hooks to each other the same way: voice-notes asks the others for `voice_note_sources`.
- **Files:** `addons/<name>/` holds its `README.md` (what it does, what it needs, how to set it up; `addon list` shows its first sentence), `rules.md` (what assistants must know while it's on, appended to their rules), and as it needs: `setup` (run by `addon enable`), `teardown` (run by `addon disable`), `next-steps` (printed after enabling or disabling it), `relay-deploy` (run by `assistant relay deploy` in `relay/`, with the Cloudflare credentials, `$WRANGLER` and `$RELAY_HOST`), `assistant-<command>` (`assistant <command>` runs it while the add-in is on; its second line, `# assistant …: what it does`, goes into `assistant help`), and other scripts.
- **Relay routes:** an add-in's routes on the relay are in `relay/src/<file>.js`, listed in `index.js`'s `ADDON_ROUTES`, and mounted after the core's only while the `ADDONS` variable names the add-in, so the Worker answers nothing for an add-in that's off. Turning one with routes on or off needs `assistant relay deploy`.
- **Plugin patches:** a patch in `bin/patch-telegram-plugin` may belong to an add-in (`Patch.addon`); it's applied only while that add-in is on.
- **Tests:** each add-in's tests are in `tests/addons/`, with a check that it does nothing while it's off.

### Slack

One Slack app (the bot) in the owner's workspace, set up from `addons/slack/slack-manifest.json`, lets people talk to their assistant from a Slack DM; [addons/slack/README.md](addons/slack/README.md) has the setup. Slack never talks to the machine: a slash command fails unless something answers it within 3 seconds and is never sent again, and the machine may be offline. So the manifest sends events, slash commands and button taps to the relay (`relay/src/slack.js`), which checks Slack's signature with the app's signing secret (`SLACK_SIGNING_SECRET`, set by the add-in's `relay-deploy`, which also writes `state/slack-manifest.json` with the relay's address as every request URL), answers at once and queues each one. `addons/slack/messages.py` turns a DM, a slash command (`/clear`, `/restart`, `/stop`, `/usage`, `/model`, `/effort`, `/plugin`, `/skills`, `/mcp`, `/help`, registered in the app) or a button tap into an `Inbound` with `app` "Slack"; `routing.py` matches people by `slack_id` in users.json, and the message goes to the same assistant as their Telegram messages, with a `[Slack from …]` header.

Each person's Session has `reply_to` (`lib/multiclaude/channels.py`): the `Chat` their latest message came from, `TelegramChat` or the add-in's `SlackChat`. The router's replies and notices (command results, skills loaded, failures, limit warnings) go there through `Session.say`; jobs, alerts, update and outage notes and approval questions stay on Telegram. A Slack message gets a 👀 reaction when it arrives (Slack has no typing for bots). A `/clear` (or `/restart`) from either app empties both chats and leaves its note in both: in the app the person wrote from, and quietly on Telegram when that was Slack, since an empty Telegram chat would show the Start button. `api.wipe_dm` reads the DM (`conversations.history`, and `conversations.replies` for threads such as a voice clip's words) and deletes every message the bot posted before then, with no age limit. A bot token can't delete what a person wrote, so their own messages go too only once they signed in: a `/clear` or `/restart` on Slack from someone without a user token offers a "Sign in with Slack" link (`api.sign_in_link`: the user scope `chat:write`, the redirect URL `https://<relay>/slack/oauth`, and a state that is an HMAC of their Slack id with the app's client secret). Slack sends them back to the relay, which shows a short page and queues a `sign_in` envelope; the router trades the code for their token with `oauth.v2.access`, revokes it if the state wasn't made for them, keeps it in `state/slack-people.json` and tells them in Slack. The app's tokens are in `state/slack.json`.

Assistants answer with `addons/slack/slack` (send, ask, edit, react, download; linked into `~/.local/bin` by the add-in's `setup`), which finds the person's DM from `$ASSISTANT_USER` (DM ids cached in `state/slack-dms.json`) and posts Markdown with `chat.postMessage`'s `markdown_text`. `slack ask` keeps its questions in `state/asks/slack-<channel>/<ts>.json`; the router updates a tapped question to show the choice and types it in like a Telegram tap. Nothing is held: `slack` exits with 1 when Slack can't be reached, and the router's notices to Slack are logged and dropped. Someone whose Slack id isn't linked is told so, and the owner gets a Telegram message with a ready `assistant slack-link <name> <id>`.

### Siri

A person talks to their assistant through an Apple Shortcut, which posts the words (`{"text": …}` or plain text) to the relay's `/voice` (`relay/src/voice.js`) with `Authorization: Bearer <voice key>`; [addons/siri/README.md](addons/siri/README.md) has the setup. `assistant voice key <name>` makes a key, replacing that person's old one, and prints it once; only its SHA-256 hash is kept, in `state/voice-keys.json`, and `assistant voice revoke <name>` forgets it. The relay can't check a key, so it queues a `voice` envelope with a request id (8 hex digits), the words, when they were said, and the key's SHA-256, never the key, and holds the shortcut's request (`askVm`). The router (`lib/multiclaude/addons/siri/`) looks the hash up: for an unknown one it puts `{"error"}` back, which the relay answers with 401. Otherwise it posts the words silently in the person's chat ("🎙️ …"), then queues them like a message under a `[Siri from <Name> · voice <id> · msg <n> · <when said>]` header. The assistant answers with `tg voice <id> TEXT` (a `tg_commands` hook), which leaves the text in `state/voice/<id>.reply` and posts it in the chat ("🔊 …") as a reply to the words; like `tg send`, it holds the message when Telegram can't be reached. The router puts the answer at the relay's `/voice/<id>`, and the relay hands it to the shortcut as `{"reply": TEXT}` for Siri to speak. After 25 seconds without an answer the relay tells the shortcut instead that it will come on Telegram, and a later answer gets 410. Requests older than an hour are cleared from `state/voice/`.

### Voice notes

The router transcribes a Telegram voice note (`attachment_kind` voice), and a voice clip recorded in Slack while that add-in is on too, before its person's assistant gets it (`lib/multiclaude/addons/voice_notes.py`). Its `on_message` hook queues a `DeliverVoiceNote`, which waits its turn in the queue like any message. Then it fetches the audio, runs `addons/voice-notes/transcribe.py` with Whisper's own venv (`~/.local/share/whisper/venv`, outside the repo, so the router stays standard-library only), posts the words silently in the chat as a reply to the note ("🎙️ …"), and types them in under a `[Telegram from <Name> · voice note · msg <n> · …]` header, with the audio still listed as an attachment. Whisper is faster-whisper 1.2.1 (with PyAV below 16, whose `av.open` dropped an argument it passes) and the multilingual `small` model in int8 on the CPU, cached in `~/.local/share/whisper/models` (about 460 MB). It runs only while a note is transcribed, on half the cores, and takes about a third of the note's length plus 2 seconds to load; `large-v3-turbo` took three times as long, so it isn't used. If fetching or transcribing fails, the person is told why and the assistant gets the note as an audio attachment. The add-in's `setup` makes the venv; [addons/voice-notes/README.md](addons/voice-notes/README.md) has the commands.

### Stickers

The router draws a Telegram sticker (`attachment_kind` sticker; the plugin passes its emoji as the text, "(sticker 🫤)") as one picture its person's assistant can look at, since a sticker's face, gesture and motion say more than its emoji (`lib/multiclaude/addons/stickers.py`). Like a voice note, its `on_message` hook queues a `DeliverSticker`, which waits its turn in the queue. Then it fetches the sticker, whose `file_path` extension gives its format (`.webp` still, `.tgs` animated Lottie, `.webm` video), and runs `addons/stickers/render.py` with the add-in's own venv (`~/.local/share/stickers/venv`: Pillow, imageio-ffmpeg with its static ffmpeg, rlottie-python), which draws it into `~/.local/share/stickers/pictures/<chat>-<msg>.png` and prints its kind, length and frame count. A still sticker is drawn as it is; an animated or video one as a grid of up to 9 numbered frames spread evenly from start to end, on light grey so a white outline shows. Video frames are decoded with libvpx, as ffmpeg's own VP9 decoder drops a sticker's transparency. The picture is listed under the message's Attachments (`attachment_lines`) as `sticker: <png> (a video sticker, 3.0 s: 9 numbered frames from start to end)`. A sticker takes about a second. If fetching or drawing fails, it's logged and the sticker goes in as before, as its emoji and `file_id`; the person isn't told, as the emoji still carries the gist. Pictures older than 7 days are deleted as new ones are drawn; they live outside `state/`, so the backup skips them.

### Locations

Stock, the plugin drops shared locations. While this add-in is on, `bin/patch-telegram-plugin` adds handlers: a location or place from an allowed sender in a private chat reaches the front desk like a message (text "(location)", "(live location)" or "(place: title, address)") with `location_lat`, `location_lon`, `location_accuracy_m` and `location_live_period` in its meta, and the router lists it under Attachments as `location: lat, lon (…)` (`attachment_lines`). The plugin also keeps the sender's latest position in `state/locations/<telegram id>.json` (`latitude`, `longitude`, `accuracy_m`, `heading`, `message_id`, `live_until`, `updated`). A live location's later positions arrive as edited messages; they only update that file and never reach Claude, so tools can follow a person without costing a turn per update. `run-user.sh` gives each session its person's file as `ASSISTANT_LOCATION`.

The OwnTracks app can keep that file up to date from a person's phone, with no Apple or Google sign-in on the machine. It posts each position to the relay's `/owntracks` (`relay/src/owntracks.js`) as JSON with HTTP Basic auth, the password being the person's OwnTracks key. Keys work as Siri's do: `assistant location key <name>` makes one and prints it once, and only its SHA-256 is kept, in `state/owntracks-keys.json` (`lib/multiclaude/keyring.py`, which the voice keys use too). The relay can't check a key, so it queues an `owntracks` envelope with a request id, the message and the key's hash, and holds the app's request for up to 10 seconds (`askVm`). The router (`lib/multiclaude/addons/locations/owntracks.py`) looks the hash up: an unknown one gets `{"error"}` back, which the relay answers with 401 so the app shows it. A `location`, or a `transition` (entering or leaving a region set in the app), becomes the person's latest position in the plugin's form, with `source` "owntracks", `updated` from the fix's `tst`, and what else it tells (`velocity_kmh`, `battery`, `regions`, `trigger`; a transition's `event` and `region`). It's written only when it isn't older than the position already there, so an update the relay kept while the machine was offline never replaces a newer live location. Other messages are taken and dropped. Either way the app gets `[]`, and also when the router hasn't answered in time, since the update stays queued. See [addons/locations/README.md](addons/locations/README.md).

### Reminders

Signing in to iCloud from a server works until Apple turns that machine away, so a person's Apple Reminders reach their assistant through an Apple Shortcut on their iPhone instead; [addons/reminders/README.md](addons/reminders/README.md) has the shortcut and its automations (a few times a day, and whenever Reminders is closed). Each run posts the open reminders to the relay's `/reminders` (`relay/src/reminders.js`) with `Authorization: Bearer <reminders key>`, keys working as Siri's do (`assistant reminders key <name>`, hashes in `state/reminders-keys.json`). The relay can't check a key, so it queues a `reminders` envelope with a request id, what the shortcut sent as it came, and the key's hash, and holds the shortcut's request for up to 10 seconds (`askVm`). The router (`lib/multiclaude/addons/reminders/`) looks the hash up: an unknown one gets `{"error"}` back, which the relay answers with 401. Shortcuts can't be relied on for the shape of a list of dictionaries, so `snapshot` reads what came leniently (a JSON array, dictionaries written as text one after another, or a title per line), keeps it as the person's latest open reminders in `state/reminders/<telegram id>.json` unless a later sync's are already there, and keeps the raw text beside it for checking a new shortcut. The answer is `{"add": [...]}`, the reminders the assistant queued with `assistant reminders add` (`outbox`, under a lock, since the assistant and the router both edit it), which the shortcut adds on the phone. They count as delivered only once the relay took the answer: when the shortcut stopped waiting (the relay answers 410, and has already told it there's nothing to add) or the relay can't be reached, they go back in the queue for the next sync. Shortcuts has no action that clearly ticks a reminder off, so the add-in only reads and adds.

### Quiet hours

A person's entry in `users.json` may add `"quiet_hours": "00:00-09:00"`, in their timezone (the window may pass midnight). During those hours everything the bot sends them on Telegram arrives silently (`disable_notification`): `BotApi.call` runs the add-in's `before_telegram_send` hook for every `send…` method, so all senders get it: the router, `tg`, jobs and `assistant notify`. A message whose sender set `disable_notification` itself keeps it, so `tg send --sound`, which sets it to false, notifies even then, for what a person wants to hear in those hours, such as a morning brief they wake up to. It reads `users.json` on every send, so an edit takes effect at once. Edits never notify anyway. Not covered: the Telegram plugin's own few messages (the "Paired!" reply) and Telegram's notices about reactions. See [addons/quiet-hours/README.md](addons/quiet-hours/README.md).

### Model fallback

When a model's safety classifier stops one of an assistant's replies, Claude Code logs a `system` entry of subtype `model_refusal_fallback` and stays on another model; `Turn` records which model's reply was stopped. The add-in's `on_transcript_entry` hook tells the person, with the classifier's category. With `"restore_model": true` in their users.json entry (a `panel_fields` setting too), the router also queues a session-only `/model` switch back to that model's family (`claude-opus-…` → `opus`), which waits until the assistant is idle like any `/model`. If the model is stopped again within 30 minutes of switching back, the conversation itself keeps setting it off, so it stays on the other model and suggests `/clear`. Others are told to send `/model opus` themselves. Fallbacks logged before the router started are ignored. See [addons/model-fallback/README.md](addons/model-fallback/README.md).

### Skill notes

Whenever an assistant loads a skill (a Skill tool call in that person's transcripts), the router posts a silent note in their chat: "🧩 Loaded the `clean-code:clean-code-python` skill". See [addons/skill-notes/README.md](addons/skill-notes/README.md).

### Backup

`assistant backup` (`addons/backup/assistant-backup`), run by cron every night at 02:30 UTC, puts what isn't in the repo into a [restic](https://restic.net) repository off the machine: `~/assistant`'s `.env`, `config.json`, `users.json` and `state/` (with a copy of the crontab, `state/backup/crontab`), `~/.claude`, `~/.claude.json`, `~/workspaces` and `~/.config/claude-usage`. It leaves out the caches that come back by themselves. Then `forget --prune` keeps 7 daily, 4 weekly and 12 monthly snapshots. `state/backup.json` names the repository, and for an `rclone:` repository the rclone program, such as a person's own wrapper with their rclone config. The password is in `state/backup-password`; the add-in's `setup` makes it, starts the repository when it's new and adds the cron line, and its `teardown` takes the line out. A run that finds another one still going stops, and each run first clears the locks that killed restic runs left (`restic unlock`), which would stop it. A file restic couldn't read (one deleted mid-backup, exit code 3) still counts as a backup. A failed night says nothing, since the storage may only be out of reach for a while. Once the last good backup (`state/backup/last-success`) is two days old, each failed night tells the owner, with restic's last error. `assistant backup restic …` runs any restic command on the repository, for listing and restoring. See [addons/backup/README.md](addons/backup/README.md).

## Access

Access stays separate from users and is never changed because a chat message asked. The owner does it on the machine:

    assistant invite [off]        # bot answers strangers with a pairing code (off: stop)
    assistant pair <code> [<name> ["Display Name"]]
                                  # approve and close pairing; with a name, also create the
                                  # workspace and session and send a welcome
    assistant add-user <name> <telegram id> ["Display Name"]
                                  # workspace and session for an id that's already allowed

Anyone who is allowed on Telegram but not in `users.json` gets a "not set up yet" reply. Add-ins that bring other apps have their own commands for linking people (`assistant slack-link`, `assistant voice key`).

## Shared bits

- **Crontab:** one per machine. Each person's lines carry a `# <name>:` comment and use `assistant job --user <name>`, and each person's `~/workspaces/<name>/jobs.md` lists them. `assistant install` adds two lines of its own, each under an `# assistant:` comment and only once: the shared sync every 10 minutes, and the health sample every 5. Cron runs in the machine's timezone, which must be UTC: the control panel works out next runs in UTC, and the assistants' rules say so.
- **`assistant notify [--user <name>]`:** messages one person on Telegram, through `tg`; the default is the owner.
- **`assistant job [--user <name>] [--tools <tools>] [--deny <tools>] [--model <model>] "<task>"`:** a one-shot `claude -p` in that person's workspace (their CLAUDE.md, memory and saved model), with the Telegram plugin off, `--permission-mode auto --permission-prompts none` (so a safety check, or a tool the person's settings put under `ask`, is denied rather than asked), no saved session, and a 1-hour timeout. It first marks the folder trusted in `~/.claude.json` (`hasTrustDialogAccepted`): Claude Code ignores the tools a folder's own settings allow until its trust dialog has been accepted, and a job never shows one. Its options are Claude Code's own flags, passed through: `--tools` with `--strict-mcp-config`, so the job gets only those built-in tools and no MCP server (a job meant only to read and take notes, `--tools Read,Edit,Write,Glob,Grep`, can't send or change anything elsewhere); `--deny` as `--disallowedTools`, which forbids tools outright, MCP ones included, while keeping the rest; `--model`, a model other than the person's saved one, so a job that runs several times a day can run on a cheaper model. Its final answer goes to the person through `assistant notify`, unless it is exactly `NOTHING`. Only one run of the same job (person and instructions) at a time: a cron tick that finds the last run still going is skipped and logged. Answers and skips are logged in `logs/jobs.log`, errors in `logs/jobs.err`. Every run, a skipped one too, also adds a line to the person's record, `state/job-runs/<name>.jsonl`, for the control panel's Activity, which keeps their last 200: when it started and finished, its title (the instructions' first line, cut at 100 characters, as its failure notice names it), its outcome (`sent`; `nothing` for an answer of exactly NOTHING; `failed` when claude failed or timed out, or Telegram refused the answer; `skipped`), its cost when the JSON result gives one, and the first 300 characters of its answer, or why it failed (Claude Code's own error from the JSON result, else how it ended). The line is written under a lock (`flock`) after the answer is sent, and a record it can't write is logged in `jobs.err`, so the bookkeeping never costs anyone their answer.
- **Status line:** `~/.claude/statusline.sh` (linked to `system/statusline.sh`) saves `~/.claude/state/statusline-<session name>.json`, which `/usage`, `/model` and `/effort` read.
- **Cost ledger:** the status line also keeps each session's running cost (Claude Code's `cost.total_cost_usd`) in `~/.claude/state/costs/<session id>.json` (`name`, `dir`, `base`, `last`, `since`); `assistant job` runs `claude -p --output-format json` and adds each job's `total_cost_usd`, a failed one's too, there as `job-<session id>.json`. A cost of 0 (a render before any API call) is skipped, and if a session's counter ever restarts well below what it had, the old amount moves into `base`, so the cost is `base + last`. `/usage` adds it all up, per person by folder (`~/workspaces/<name>`, the front desk's folder, anything else as "other").
- **Plan limits:** `~/.local/bin/claude-usage` (linked to `system/claude-usage`) fetches the plan's usage with its own `user:profile`-only login, stored in `~/.config/claude-usage/`. That login can't run inference. The status line runs it in the background once its cache, `~/.cache/claude-usage/usage.json`, is 5 minutes old. `/usage` reads the same cache and refetches if it's stale. The limits are account-wide, so every person sees the same numbers. When someone sends a request, the router also checks the cache and tells that person once per limit window as a limit passes a level (`router/limits.py`: 80%, 90% and 99% of the 5-hour limit; 25%, 50%, 75%, 90% and 99% of the weekly ones, with a calm note below 75%). It never waits for a fetch to do this; a stale cache triggers a background refresh for the next message. What each person has been told is kept in `state/limit-alerts.json`, so a router restart doesn't repeat it. A new window is detected when `resets_at` jumps by more than 10 minutes, because the API's value drifts by about a second between fetches.
- **Shared plugins, skills and marketplaces:** each person's assistant installs these only at project scope, in `~/workspaces/<name>/.claude/` (the assistants' rules say how). `bin/shared.py` (the `multiclaude.sharing` package; `assistant shared sync`, from cron every 10 minutes and by an assistant right after it installs something) moves an item to user scope, `~/.claude`, once every person in `users.json` has it, and deletes the per-person copies:
  - a plugin enabled as the same `name@marketplace`: `claude plugin install --scope user`, then `claude plugin uninstall --scope project|local --keep-data` in each workspace. It waits until its marketplace is at user scope (the official one always is).
  - a marketplace declared with the same source: written to `extraKnownMarketplaces` in `~/.claude/settings.json` with `autoUpdate: true`, so Claude Code refreshes it and its plugins at every start (it takes `autoUpdate` only from user settings).
  - a skill folder with identical files: copied to `~/.claude/skills/`.

  New people start with nothing shared. When someone is added to `users.json`, everything shared goes back into the workspaces of the people who had it, marketplaces included (declared again in their project settings), and leaves `~/.claude`; an item moves up again once the newcomer has it too. `state/shared.json` keeps who had what's shared (`people`), which is how a run tells who is new (its first run only notes who is there), and `assistant add-user` runs a sync before it starts the newcomer's session (`--wait`, so a sync already running finishes first). While something can't go back yet (an install failed), nothing new is shared and the next run tries again. When someone turns a shared plugin or skill off in their own settings (`enabledPlugins` false, `skillOverrides` "off"), it goes back into everyone else's workspace, the override is removed, and it leaves `~/.claude` (a skill is kept in `state/shared-trash/`); its marketplace stays shared. `state/shared.json` lists what the script moved, and it changes nothing else in `~/.claude`. Anything else that appears there (beyond what was there on the first run) is reported to the owner once, since that means an assistant installed at user scope. Skill folders in `state/shared-trash/` are deleted after 30 days. The owner gets a Telegram message for every move. The front desk gets each shared plugin set to false in `~/assistant/.claude/settings.local.json`, so it never loads their tools. Every other Claude session on the machine does see them. Claude Code also reads skills from parent folders (`~/workspaces/.claude/skills` would work) but ignores settings there, so plugins and marketplaces can only be shared from `~/.claude`.

## Source control

The repo holds code, docs and templates only. Secrets and per-person data stay out (see `.gitignore`): `.env`, `config.json`, `users.json`, `state/`, `logs/`, `.claude/settings.local.json`, the relay's `node_modules/` and `.wrangler/`, and caches. `assistant`, `tg`, `takeover`, `claude-usage` and the status line are symlinks into the repo, so they follow it (as does `slack`, linked while that add-in is on). The two systemd units and `~/workspaces/.claude/CLAUDE.md` are rendered copies, of `system/*.service` and `system/workspaces-CLAUDE.md` with the add-ins' rules: `assistant install` writes them again after an update. `addons/slack/slack-manifest.json` is a template: `assistant relay deploy` writes the real one, with the relay's address, to `state/` while the slack add-in is on.

## Code layout and tests

- `bin/`: the programs. `assistant`, `run.sh` and `run-user.sh` are bash and source `bin/common.sh` (paths, the tmux socket and size, `.env`, users.json and config.json lookups). `watcher.py`, `shared.py`, `health.py`, `tg` and `takeover` are thin Python entry points that put `lib/` on `sys.path`; systemd runs `watcher.py`, and `assistant` runs `shared.py` and `health.py`, with `python3 -I`, which leaves the script's own folder off it. `patch-telegram-plugin` (patches the plugin's `server.ts`) stands alone.
- `lib/multiclaude/`: the Python code, standard library only.
  - Shared: `paths` (every location, `/proc` included, each movable by an environment variable for the tests), `jsonfile` (lenient reads, atomic writes, locked edits), `keyring` (the keys an app such as Siri, OwnTracks or a Reminders shortcut shows for a person, kept as hashes), `log`, `config` (the owner's `config.json`: the bot's name, the add-ins that are on, the health alerts' numbers), `bot` (the bot's name), `users` (the core's fields of each person, and their entry as it is for add-ins), `cronjobs` (a person's scheduled jobs in the crontab: next runs, the instructions they give, pause and resume), `jobruns` (reading what each person's job runs did), `telegram` (the Bot API client, IPv4-first connects, rich-message blocks and copy buttons, chat history records, held messages), `websocket` (a small client, for the relay and a browser's stream), `channels` (`Chat`, a person's chat in one app, where the router's notices and its own questions go: `TelegramChat`, or an add-in's), `questions` (keeping questions with buttons for the router to answer taps, for `tg ask`, add-ins' apps and the router), `claude_cli` (`claude` subcommands, with the `env` the folder's settings give its sessions), `tmux`.
  - `router/`: `desk` (the loop), `session` (a session's terminal, transcript and claude process), `turn` (whether it's working), `transcript`, `inbound` (parsing the plugin's messages), `work` (the queue items and the worker threads), and one module per command or job: `about` (`/help`, the command menu and the bot's description), `switching`, `usage`, `limits`, `upgrade`, `plugins`, `asks`, `approvals`, `mcp_login`, `claude_ui`, `relay_entrance` (`state/relay.json`, the WebSocket in, and the PUTs back out), `panel` (the control panel), `recovery` (network outages and failed turns), `poller` (restarting the front desk when its Telegram poller is gone).
  - `addons/`: the add-ins' code, a module or package each (`voice_notes`, `locations/`, `reminders/`, `quiet_hours`, `model_fallback`, `skill_notes`, `slack/`, `siri/`), and in `__init__` the mechanism and its list of hooks.
  - `sharing/`: `people`, `sync` (the sync's steps and its manifest), `skillfiles`, `commands` (`/plugin`, `/skills`), `mcp` (`/mcp`), `reply`, `listing`, `inventory` (the plugins and skills the control panel lists).
  - `health/`: the machine's health. `machine` (reading `/proc`, the disks, the router and the sessions), `history` (the samples kept, and the panel's day), `alerts` (the rules, their standings and the owner's messages), `words` (sizes and shares), `sample` (a run from cron), `status` (`assistant health`).
  - `takeover/`: browser take-overs. `browser` (the session: its stream server and viewport), `stream` (the bridge to it), `viewport` (fitting the viewport to the person's screen, and putting it back), `fields` (the text fields in view and the focus, for a phone's keyboard), `controls` (the page's actions as stream events), `page` (the page's server) and `page.html`, `tunnel` (cloudflared), `notice` (the link on Telegram), `run` (the take-over, the command's options and exit status).
- `addons/<name>/`: each add-in's README, rules and scripts (see Add-ins).
- `relay/`: the relay, a Cloudflare Worker (`src/index.js` for the queue, the control panel's routes and mounting the add-ins' routes, `src/vm.js` for the way to the machine, `src/panel.js` for the control panel, `src/slack.js`, `src/voice.js`, `src/owntracks.js` and `src/reminders.js` for the slack, siri, locations and reminders add-ins, `src/secrets.js`, `wrangler.toml`), the control panel's page in `public/app/` (served as static assets; `format.js` words its times, money, sizes and job runs, `sparkline.js` draws the machine's day), and Node tests in `relay/test/`.
- `system/`: the systemd units and the assistants' rules, rendered by `assistant install`, and the status line and `claude-usage`, linked by it. `templates/CLAUDE.md.tmpl`: a new person's CLAUDE.md. `assets/architecture.svg`: the diagram at the top of this file, an SVG drawn by hand. `.claude/settings.json`: turns the Telegram plugin on for the front desk's folder only.
- `tests/`: pytest, run by `./check` together with ruff, shellcheck and the relay's tests (`node --test`). It uses `uvx`, so nothing is installed system-wide, and needs Node. Each add-in's tests are in `tests/addons/`, and Claude Code screens the router reads are in `tests/fixtures/`. The tests never touch the live system: paths point into a temporary folder, `/proc` is a fake one there, the `claude` CLI, `sudo`, `systemctl`, `crontab`, the Bot API, Slack, `agent-browser` and its stream server, and `cloudflared` are fakes, and tmux is recorded. Run `./check` before every commit.
- Docs: every change updates its docs in the same commit, so they always describe the code as it is. This file says how it works and why, and the diagram at its top shows the pieces and the paths between them; README.md says what someone setting it up or using it needs; `system/workspaces-CLAUDE.md` what assistants must know to use or explain it; each add-in's README.md and rules.md the same for that add-in; CLAUDE.md the front desk session's own behaviour. Rewrite the passage that covers the change rather than appending to it, and delete what no longer applies.
